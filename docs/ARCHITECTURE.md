# FrameLab Integrated Application Architecture

FrameLab will keep the browser experience as the primary product and add persistent application services only for work that benefits from durable storage, user isolation, and job coordination. The optional worker remains separately deployable and entirely under the operator’s control. The web application must stay useful when no worker is connected: projects, asset metadata, transcript editing, beat maps, and render plans remain available; only media processing and final exports are unavailable.

## Application Boundary

| Layer | Responsibility | Must work without an optional worker |
|---|---|---|
| Creator web app | Authentication, project workspace, asset metadata, editor state, transcript timing, beat maps, presets, render planning, status visibility. | Yes. |
| Application API and database | User-owned project records, asset records, transcript data, beat maps, render-job records, worker registration, audit timestamps. | Yes. |
| Managed file storage | Media files and export artifacts subject to the deployment operator’s storage configuration. | Metadata and local browser workflows still work if no upload is used. |
| Optional media worker | Fetches authorized render jobs, performs a configured media task, uploads resulting artifacts, and reports status. | No. It is opt-in and disconnected by default. |

## Core Domain Model

The application uses a single vocabulary across the interface and API. A `Project` owns ordered `Asset` records, a `Transcript` with editable `TranscriptToken` entries, a `BeatMap`, saved `Preset` choices, and a history of `RenderJob` records. An `Export` is created only after a worker completes an authorized job.

| Resource | Essential fields | Ownership rule |
|---|---|---|
| Project | name, aspect ratio, canvas mode, active preset, status | Belongs to one authenticated user. |
| Asset | project id, display name, media kind, upload key, duration, order | Must reference media the operator is entitled to process. |
| Transcript token | project id, line number, position, text, start and end timing | Editable by the project owner. |
| Beat map entry | project id, timestamp, strength, ordering | Editable by the project owner. |
| Render job | project id, requested format, plan JSON, status, worker id, error message | May move only through valid job states. |
| Worker registration | name, callback URL or pull mode, encrypted shared secret reference, status | Controlled by the deployment operator. |

## Render Job State Machine

`draft` → `queued` → `processing` → `review` → `completed`

`queued` and `processing` may transition to `failed` with a human-readable message. A retry creates a new `queued` job rather than mutating a completed export. The worker never decides that an upload is safe to process; the application authorizes a job before it becomes available to the worker.

## Worker Contract

The first worker integration is pull-based. A registered worker authenticates to request one queued job, acknowledges the job before processing, periodically posts progress, and posts either a structured completion payload or a failure payload. This avoids requiring the public application to directly invoke a machine on the operator’s network.

The processing payload contains a project plan, asset identifiers, output settings, and an expiring file-access location generated by the application. It never contains another user’s data or unrestricted storage credentials. Workers must treat all media and text as untrusted input and should enforce their own size, duration, and format restrictions.

## Free and Open-Source Promise

FrameLab’s application code is MIT licensed. The integrated app does not depend on a paid render API. A self-hosting operator may incur infrastructure costs for storage, bandwidth, or compute, but those are choices of deployment rather than application fees. The worker contract is documented and replaceable so operators can use a renderer suitable for their own hardware and rights requirements.
